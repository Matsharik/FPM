## Утверждено вместе с планом (11.11)
- D1. У каждого KPI есть файл ряда, включая `weighted`: в нём живут флажки, точки вычисляются.
- D2. Статус считается по последнему дневному значению (`status_window_days: 1`; при большем значении — по среднему за окно). Между target и warn статус зелёный (severity уже > 0); порог считается пройденным при равенстве.
- D3. Часы стоят и двигаются только через `/api/demo/advance`: иначе нет побайтовой воспроизводимости. Точка за сутки появляется, когда сутки закрыты. Часовой пояс — фиксированное смещение из `settings.yaml` (на Windows нет tzdata).
- D4. Правки словаря через API пишутся в `data/glossary.json`; `config/glossary.yaml` остаётся исходником, reset его восстанавливает.
- D5. Weighted: если у слагаемого нет значения за день, веса перенормируются по остальным.
- D6. Recheck разрешён из любого незакрытого статуса (иначе невыполнимо «без assign даёт failed»). Точка отсчёта — назначение действия, без него — момент сигнала. Итог считается по KPI карточки. *Уточнено D68: без назначенного действия `verified` невозможен.*
- D7. Генератор — чистая функция от (узел, KPI, дата): только `random()` со строковым сидом и арифметика, без `gauss`, `sin`, numpy. Python гарантирует стабильность между версиями только для `random()`.
- D8. `cause.confidence` карточки берётся из KPI «доля подтверждённого брака» ОТК.
- D9. Узел без входящих `inherit`-связей доступен создавшему его builder'у; `validate` показывает его как «вне зон».
- D10. `uvicorn` без `[standard]` плюс явный `PyYAML`: меньше бинарных зависимостей на чистой машине.
- D11. Одна карточка на инцидент: KPI, лежащий на trace открытой карточки, новую не порождает (ответ 2 к плану).
- D12. Карточку видит тот, у кого в зоне узел сигнала, узел первопричины или исполнитель; чужое урезается (ответ 3 к плану).
- D13. Старые маршруты `/manager`, `/builder`, `/qc`, `demo.py`, `demo_network.py` удалены; контракт — `/api/*` (ответ 4 к плану).

## Ф1
- D22. Единственная связь KPI всегда весит 1 (переданный вес игнорируется); новая связь к KPI, у которого уже есть связи, не может весить 1 — иначе остальные обнулятся.
- D23. Веса хранятся с шестью знаками; остаток округления отдаётся самой тяжёлой связи, поэтому сумма равна 1 точно (три равные связи: 0.333333, 0.333333, 0.333334).
- D24. `PUT /weights?normalize=true` принимает любые положительные числа (важны пропорции); без флага каждый вес должен быть в (0; 1], а сумма равна 1.
- D25. Удаление узла каскадно удаляет его связи и перенормирует веса соседних. Удаление KPI удаляет связи от него и сбрасывает `to_kpi` у связей на него; если на KPI опирается `weighted`-KPI — 409 `in_use`.
- D26. В записи KPI в `node.json` хранится копия `unit`: единицы `weighted` проверяются без чтения рядов. Источник истины для KPI со словарной метрикой — словарь (Ф2).
- D27. `links.json` — объект `{"schema_version": 2, "links": [...]}`; файл переписывается целиком и атомарно, поэтому инварианты весов не бывают нарушены «наполовину».
- D28. Записи журнала сверх полей промпта содержат `seq` (порядок внутри одного момента часов) и `nodes` (узлы объекта — для фильтра по зоне в Ф5).
- D29. Новые сообщения об ошибках — на русском; старые английские сообщения Егора (`network`, `timeseries`) не переводились.
- D30. Проверки из `demo_network.py` перенесены в `tests/test_network_core.py`.
- D31. `QualityNetwork.version` растёт при любой записи — на нём в Ф2 строится кэш вычисляемых значений.

- D34. Сверх минимального списка раздела 4 в словарь добавлены только метрики, названные в самом промпте: `production_time` (срок 24 ч / 72 ч), `defect_escape_rate` («ОТК: пропуск брака», 10.2), `service_availability` (IT, 10.1). «Входной брак материалов» добавляется через API в сценарии конструктора.

- D36. `overrides` KPI: `{"crit": 6}` действует во всех профилях, `{"season": {"crit": 7}}` — только в профиле; после наложения порядок порогов проверяется.
- D37. `display.relative`: `pct_of_target`, `index` (оба — значение / цель × 100), `share` (проценты → доля 0..1), `as_is`. Первые два запрещены при `target = 0` и у метрик без порогов.
- D38. При `allow_money = false` отвергается не только денежная единица (`unit`, `display.natural`, единица KPI без метрики), но и непустой `money_factor`: это уже абсолютная сумма в конфиге.
- D39. Единицу метрики, которая уже используется в KPI, менять нельзя (409 `in_use`): копии единицы лежат в узлах и участвуют в проверке `weighted`.
- D40. У KPI со статусом по флажкам severity равна 0 / 0,5 / 1 для green / yellow / red — она нужна расчёту вкладов (Ф3).
- D41. Профиль сезона выбирается по месяцу часов стенда; у метрики без профиля `season` в сезон действуют пороги `default`.
- D42. Дневная агрегация берёт все точки не позже «сейчас», включая текущие незакрытые сутки (контролёр мог уже внести точку); сид и перемотка пишут только закрытые сутки.
- D43. `GET /api/kpi/{n}/{k}` по умолчанию отдаёт сырые точки (`agg=raw`), `agg=day` — дневные; у `weighted` точки всегда дневные, с меткой начала местных суток.
- D44. Статус узла в `network` теперь считает `core.kpi` (через `set_status_resolver`); флажки вида info/warning/critical у KPI с порогами — только аннотации.

## Ф3
- D46. Шаг trace содержит `via` (связь, по которой пришли), `chosen` (по которой пошли дальше) и `alternatives` — до двух лучших непройденных связей с ненулевым вкладом. На последнем шаге при остановке по порогу альтернативы — лучшие связи, по которым не пошли (так «Нагрузка смены» видна на шаге «Сборка»).
- D47. Порог trace строгий: вклад, равный `trace_min_contribution`, продолжает путь. Порядок проверок: нет связей → порог → зона. Сверх промпта: `no_kpi` (узел-цель без KPI) и страховочная `max_depth`.
- D48. Цель вне зоны: у связи остаются id, вес, имя и владелец узла, общий статус; `target_kpi`, severity, вклад и доля — `null`. Корень trace — граничный узел с `kpi: null`, `visible: false`. Зона пока параметр `zone`, API передаёт `None` (Ф5).
- D49. Id связей сравниваются по номеру (`L-10000` после `L-9999`), а не как строки.
- D50. `summary` вкладов — «Метрика: Узел 97%, Узел 3%»: только видимые связи с ненулевым вкладом, доли в целых процентах.
- D51. Прогноз: окно `forecast_lookback_days` и горизонт отсчитываются от последних суток с данными (не от часов); меньше 7 суток — 200 с `enough_data: false`; недельная сезонность — при ≥ 14 сутках; тренд и сезонность подгоняются совместно (поочерёдно, 50 раундов, без случайности); σ — по остаткам с n−2 степенями свободы; коридор не обрезается снизу.
- D52. Пересечение порогов в прогнозе — по центральному значению и порогам **на дату прогноза** (с декабря — профиль `season`); в режиме `relative` значения пересчитываются по текущим порогам, как и ряд. Неверный `horizon` — 400 `invalid_horizon`.
- D53. Мини-организация «Брак» для тестов — `tests/scenario.py`. Сид Ф4 должен её повторять: «Сборка: доля брака» → три сотрудника и «Смены: нагрузка» с равными весами 0,25; нагрузка жёлтая, но не выше 115 % (вклад < 0,15), иначе trace уйдёт в «Смены».

## Ф4

- D56. Таблица переходов — в `core/deviations.py` (`TRANSITIONS`); `assigned → assigned` — переназначение. Переход в `assigned` требует text, владельца (логин или узел) и due_at; момент назначения пишется в `action.assigned_at` и служит точкой отсчёта перепроверки и веток. *Заменено D67: смена исполнителя `assigned_at` не двигает; ветки отсчитываются от `first_assigned_at`.*

Нет данных после отсчёта — 409 `no_data_after`; KPI без порогов — 409 `no_thresholds`. *Заменено D69 в части окон (целые сутки, длина окна); пороги на сутки отсчёта и оба кода 409 остаются.*
- D58. Ветка будущего выбирается по последней карточке с сигналом сценария, где действие назначалось: с суток назначения — `with_action` (смещение от назначения), до них — `no_action` (смещение от старта сценария). - D60. Фон держится около цели профиля на дату, severity ≤ 0,15. Сверх промпта в сценарий добавлен «ОТК: пропуск брака» 0,8 % (зелёная зона, выше цели 0,5): иначе строка вкладов была бы «Сборка 100%».
- D61. Флажок карточки ставится на ряд сигнального KPI в момент обнаружения: `kind=critical`, `ref=DEV-…`. Аннотация сценария — флажок `kind=annotation` на рядах Сборки и Поддержки.

## Ф4: исправления по независимой проверке (12.11, согласовано с владельцем)
Находки — в `docs/FIX_NOTES.md`; исправлены 1–4 и часть 5 (окно «после»).
- D67. Ветка `with_action` привязана к первому назначению действия по сигналу: `action.first_assigned_at` пишется один раз, `Demo.advance` берёт самый ранний момент по всем карточкам сигнала. Повторный переход в `assigned` из `assigned`/`in_progress` — смена исполнителя или срока: `assigned_at` не меняется. Переход в `assigned` из `open`, `failed`, `escalated` — новое действие: `assigned_at` сдвигается (от него считается перепроверка), кривая не перезапускается. Заменяет D56 (в части «каждое назначение пишет `assigned_at`») и D58 (в части «последняя карточка, смещение от её назначения»).
- D68. Карточка без назначенного действия не может стать `verified`. Перепроверка без действия: не прошла — `failed` (как в D6), прошла — `closed` с `resolution: "self_resolved"` (KPI пришёл в норму сам). В `recheck_success_rate` входят только завершённые перепроверки назначенных действий: записи `pending` и записи без действия не считаются. Уточняет D6.
- D69. Окна перепроверки считаются от момента, а не от суток: after — точки из `[отсчёт; min(сейчас, отсчёт + window_days)]`, baseline — отрезок той же длины перед отсчётом; значение окна — среднее дневных значений по точкам внутри него. Точка, внесённая до назначения, в «после» не попадает. Пока после отсчёта не прошло `settings.recheck_min_days` (3) суток, итог `pending`: запись добавляется в `rechecks[]`, статус не меняется. `window_days` меньше `recheck_min_days` — 400 `invalid_window`. Поля окна `from`/`to` — моменты ISO, а не даты; в записи появились `result`, `without_action`, `elapsed_days`, `min_days`; `passed` при `pending` равен `null`. Заменяет D57 в части окон.
- D70. `window_days` остался верхней границей окна «после» (по умолчанию 7), хотя согласованная формулировка — «до сейчас». При вызове раньше 7 суток окно равно прошедшему времени, как и согласовано.

- D72. Демо-ветка по-прежнему начинается с суток назначения: точка этих суток (метка 00:00) берётся из `with_action`, хотя действие назначено в 09:00. ## Ф5
- D73. Утечки о невидимых узлах (FIX_NOTES №10) закрыты так: у цели вне зоны `to_kpi` и `target_kpi` — `null`, `status` — общий статус узла, а не её KPI; доли и `total_contribution` считаются только по видимым связям (иначе доля видимой связи выдаёт сумму скрытых вкладов), число скрытых — в `hidden_links`; в списке вкладов скрытые связи идут после видимых по id связи; в альтернативы trace скрытые связи попадают по id независимо от вклада.
