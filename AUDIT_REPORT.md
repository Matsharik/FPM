## 5. Модель данных и граф

### 5.1. Узел
Память: `graph.Node` (`graph/graph.py:6-16`) — `id:int`, `name`, `description`, `parameters: dict[str,int]`, `directory`, `parents:set[int]`, `children:set[int]`.
Диск (`network/network.py:217-229`), реальный пример из `local/nodes/002/node.json`:
```json
{ "schema_version": 1, "id": 2, "name": "Отдел кадров", "description": "",
  "parameters": { "additionalProp1": -14, "additionalProp2": 365, "additionalProp3": 1 },
  "parents": [0], "children": [] }
```
- **Типов узлов нет** (отдел / сотрудник / продукт / партнёр не различаются; можно лишь кодировать int-параметром).
- **Параметры — только целые числа** (`graph.py:26-27`, `server.py:44, 54-55`): нельзя хранить ФИО владельца, срок, текст, проценты с дробью.
- id — последовательные int; после удаления узла с максимальным id и перезапуска **id переиспользуется** (`graph.py:72`, `network.py:149-162`). Ссылки на старый узел (например, из будущего журнала решений) начнут указывать на другой узел.
- Ответ API по узлу (`network.py:290-300`) добавляет `metrics` (имена) и `status` (собственный цвет).

### 5.2. Рёбра
- Ровно один тип ребра: `parent → child`, семантика — «**родитель зависит от ребёнка**» (`network.py:447`). Хранится дублями: в `children` родителя и `parents` ребёнка; при загрузке связь берётся с любого конца (`network.py:164-173`).
- **Несколько родителей — да** (проверено smoke-тестом).
- **Циклы запрещены** (`graph.py:109-114`) → это строгий DAG.
- Атрибутов у ребра нет (тип, вес, «влияет на»/«подчиняется», описание) — рёбра это голые множества id (`graph.py:15-16`).

### 5.3. Метрика (временной ряд)
Файл `nodes/NNN/<metric>.tseries.json` (`timeseries/codec.py:30-39`):
```json
{ "schema_version": 1, "name": "defect_rate", "unit": "%", "tags": {"site": "assembly"},
  "points": [ {"ts": "2026-05-01T00:00:00Z", "value": 1.94}, ... ],
  "flags":  [ {"ts": "2026-05-30T00:00:00Z", "kind": "critical", "values": [6, 2],
               "label": "Брак 5.9% при цели 2%", "ref": "DEV-2026-0002"} ] }
```
- Точки: уникальный ts, отсортированы; повтор ts перезаписывает (`series.py:263-296`). Пачка атомарна.
- Флажки: `kind` — свободная строка, `values` — «смысл пока не определён» (`series.py:128-129`), `ref` — «**id карточки отклонения**» (`series.py:130`) — то есть автор заложил место под Deviation, но самой карточки нет.
- Агрегирования (день/неделя), порогов, целевого значения, прогноза — **нет**.
- Статус-светофор считается **только по флажкам**: последний из `info|warning|critical` даёт green|yellow|red; без флажков и с точками — green, без точек — unknown (`network/status.py:22-32`). Узел — худший из своих метрик (`network.py:280-288`); `deep=true` — худший по всем потомкам (`network.py:623-634`). Значения точек на цвет не влияют.

## 7. Ответы на архитектурные вопросы

**Типы рёбер.** Не выражаются. Есть один тип «родитель зависит от ребёнка» (`network.py:447`), у ребра нет атрибутов (`graph.py:15-16`). Добавить «влияет на» как второго родителя технически можно (smoke: Поддержка→Сборка — 201), но:
- такое ребро неотличимо от подчинения → ломает оргдерево, «видимость поддерева» и «подчинённых»;
- `status?deep` и `get_children` пойдут по нему так же, как по подчинению (`network.py:633`) — красный узел производства окрасит поддержку (иногда это даже нужно, но неуправляемо);
- общая проверка на цикл (`graph.py:109-114`) запретит законные процессные петли (Возврат → Сигнал) и встречные влияния между ветками.

Ваша гипотеза подтверждается: **одного дерева «подчиняется» мало, и текущий граф это не разделяет.** Что менять (минимально): хранить рёбра отдельным списком `{from, to, type}` (`subordinate | influences | flow`), проверять ацикличность только для `subordinate`, параметризовать обходы/статусы типом ребра (`deep` по `subordinate`, «поиск причины» — по `influences`). Затрагивает `graph.py`, формат `node.json` (`network.py:217-229`, загрузка `:149-195`) и `EdgeCreate`/маршруты (`server.py:58-60, 260-271`). Оценка — в разделе 8.

**Сущности.** Есть: узлы + метрики-ряды + флажки. Минимальной доработкой: Deviation (из Flag + `ref`), «до/после» для решения (из `get_range`), права по поддереву (из `get_children` + восстановленного `visibility`). С нуля: Event, Status этапов, Decision log, User/Role, Audit log, Glossary, генератор синтетики 5 источников.

**Конфиг.** Узлы и метрики — данные (JSON на диске, CRUD через API), не код: подразделение добавляется одним `POST /builder/nodes` (проверено). Но декларативного файла конфигурации, который можно положить в репозиторий и загрузить одной командой, нет; описания метрик (определение, формула, источник, владелец) нет вообще. «Конструктор за минуты» сейчас = «через Swagger», а не «правкой YAML».

**Деньги.** В коде, данных и API абсолютных сумм нет (grep пуст, раздел 6 п. 9). Технического запрета нет.

**Прогноз.** Нет ничего: ни тренда, ни скользящего среднего, ни экстраполяции.

**Детерминизм демо.** Внешних API, LLM, сети нет; синтетика в `demo_network.py` с фиксированными сидами. Офлайн — да. Но демо-сценария для жюри нет.

**Хранилище.** JSON-файлы, атомарная запись через временный файл + `os.replace` с повтором для OneDrive (`network.py:88-114`, `storage.py:23-55`). Перезапуск выдерживает (проверено). Ограничения:
- один процесс: кэш серий в памяти (`network.py:131`) + `RLock` — при нескольких воркерах uvicorn или двух серверах на одной папке данные разойдутся (ГИПОТЕЗА по коду, не проверялось);
- связь пишется в два `node.json` не атомарно; при сбое между записями `remove_edge` связь «воскреснет» при загрузке, потому что берётся с любого конца (`network.py:164-165, 464-466`) — ГИПОТЕЗА по коду;
- переиспользование id после удаления (5.1).
Для идеи «решение сохранили — проверили позже» хранилище подходит, но **сами решения хранить негде**.

**Масштаб.** 8 плиток + 30–60 узлов + год дневных точек: каждый вызов `_info` считает статус, читая все метрики узла (`network.py:280-300`), `/manager/nodes` — все узлы. Для 60 узлов × ~5 метрик × 365 точек это порядка 100 тыс. точек в памяти — ГИПОТЕЗА: справится без переписывания. `/manager/nodes` фактически отдаёт весь граф (у каждого узла есть `parents`/`children`), так что отдельный эндпоинт «весь граф» для фронта не обязателен. Понятия «плитка» нет — его придётся вводить (например, узел с типом `tile` или агрегат по набору метрик).
